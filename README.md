# Бронь без конфликтов

Учебный веб-сервис бронирования ресурсов образовательной организации.
Один ресурс невозможно забронировать на пересекающееся время — гарантия
обеспечивается на уровне базы данных, а не интерфейса.

## Назначение

Сервис предназначен для бронирования переговорных комнат.
Каждая комната — отдельная единица ресурса с карточкой и полным бронированием
(нельзя забронировать «половину комнаты»).

Пользователь: вход → каталог → карточка → выбор свободного времени →
форма → подтверждение → запись в разделе «Мои бронирования».
Администратор дополнительно управляет комнатами, видит все брони,
отменяет чужие брони с причиной и просматривает аудит.

## Вид ресурса

Переговорные комнаты (5 единиц в учебных данных).

## Стек

- **Node.js 24** (в CI — 24, локально достаточно ≥ 20)
- **Express 4** — HTTP-сервер
- **PostgreSQL 16** — СУБД
- **pg** (node-postgres) — драйвер БД
- **node-pg-migrate** — миграции
- **jsonwebtoken** — JWT
- **bcryptjs** — хеширование паролей
- **pino / pino-http** — структурные технические логи
- **HTML + CSS + Vanilla JS** — фронтенд (без сборки)
- **Docker Compose** — PostgreSQL и pgAdmin
- **GitHub Actions** — CI/CD

## Правила времени

- Ресурсы доступны ежедневно **08:00–22:00 МСК**.
- Шаг выбора времени — **30 минут**, продолжительность — **от 30 минут до 4 часов**.
- Бронирование целиком помещается в один рабочий день; окончание позже начала.
- Начало **не в прошлом** и **не позднее чем через 30 суток** от текущего момента.
- Проверка выполняется по **серверному времени**.
- API принимает дату со смещением часового пояса; БД хранит однозначный момент (UTC, тип `timestamptz`).
- Интерфейс явно указывает московское время.

## Правила пересечения интервалов

Интервал имеет вид `[начало, окончание)` — момент окончания свободен.
Конфликт существует, когда:

```
начало_новой < окончание_существующей  И  окончание_новой > начало_существующей
```

| Существующая | Новая | Результат |
|---|---|---|
| 10:00–11:00 | 09:00–10:00 | Разрешено |
| 10:00–11:00 | 11:00–12:00 | Разрешено |
| 10:00–11:00 | 10:00–11:00 | Конфликт |
| 10:00–11:00 | 09:30–10:30 | Конфликт |
| 10:00–11:00 | 10:30–11:30 | Конфликт |
| 10:00–11:00 | 09:00–12:00 | Конфликт |

Проверка относится к одному ресурсу и активным записям.
Отменённые записи не занимают время. Разные ресурсы могут бронироваться одновременно.

## Правила отмены

- До начала записи владелец может отменить её.
- Администратор может отменить любую запись **с обязательной причиной**.
- Начавшиеся и завершённые записи отменять нельзя.
- Повторная отмена не создаёт нового изменения состояния.
- При отмене сохраняются запись, исполнитель, время и причина.

## Правила доступа

- Владелец новой записи определяется сервером по проверенному JWT.
  Переданные клиентом `owner_id` и `role` не предоставляют прав.
- При чтении и отмене сервер проверяет владельца записи либо административные полномочия.
- Обычному пользователю чужая запись возвращается как **404** (не раскрываем существование).
- Административные маршруты при обращении обычного пользователя возвращают **403**.
- Защита сохраняется при прямом запросе, даже если кнопка скрыта в интерфейсе.

## Отключение и удаление

- Отключённый ресурс (`is_active = false`) недоступен для новых бронирований.
- Существующие записи сохраняются; администратор при необходимости отменяет будущие записи с причиной.
- Физическое удаление ресурсов и бронирований через интерфейс не реализуется.

## Схема данных

```
users
  id            serial PK
  name          varchar(100) NOT NULL
  login         varchar(50)  NOT NULL UNIQUE
  password_hash varchar(255) NOT NULL
  role          varchar(20)  NOT NULL CHECK (role IN ('user','admin'))
  created_at    timestamptz  NOT NULL DEFAULT now()

resources
  id          serial PK
  name        varchar(100) NOT NULL
  description varchar(500)
  location    varchar(100) NOT NULL
  is_active   boolean      NOT NULL DEFAULT true
  created_at  timestamptz  NOT NULL DEFAULT now()

bookings
  id            serial PK
  resource_id   integer NOT NULL REFERENCES resources(id) ON DELETE RESTRICT
  owner_id      integer NOT NULL REFERENCES users(id)     ON DELETE RESTRICT
  start_time    timestamptz NOT NULL
  end_time      timestamptz NOT NULL
  purpose       varchar(300) NOT NULL CHECK (char_length(purpose) BETWEEN 5 AND 300)
  status        varchar(20)  NOT NULL DEFAULT 'Active' CHECK (status IN ('Active','Cancelled'))
  created_at    timestamptz  NOT NULL DEFAULT now()
  cancelled_by  integer REFERENCES users(id) ON DELETE SET NULL
  cancelled_at  timestamptz
  cancel_reason varchar(300)
  CHECK (end_time > start_time)

idempotency_keys
  id           serial PK
  user_id      integer NOT NULL REFERENCES users(id) ON DELETE CASCADE
  key          varchar(100) NOT NULL
  request_hash varchar(64)  NOT NULL
  booking_id   integer REFERENCES bookings(id) ON DELETE SET NULL
  created_at   timestamptz NOT NULL DEFAULT now()
  UNIQUE (user_id, key)

audit_events
  id          bigserial PK
  occurred_at timestamptz NOT NULL DEFAULT now()
  actor_id    integer REFERENCES users(id) ON DELETE SET NULL
  action      varchar(50) NOT NULL
  object_type varchar(50) NOT NULL
  object_id   integer
  result      varchar(20) NOT NULL
  trace_id    varchar(50)
```

### Индексы и их назначение

| Индекс | Назначение |
|---|---|
| `resources(location)` | фильтр по локации в каталоге |
| `ix_bookings_resource_time (resource_id, status, start_time, end_time)` | проверка пересечений при каждой попытке брони |
| `ix_bookings_owner (owner_id, start_time)` | страница «Мои бронирования» |
| `audit_events(occurred_at)` | последние события в админке |
| `uq_idempotency_user_key (user_id, key)` | защита от дубликатов при повторе запроса |

## API

Базовый префикс: `/api`.
Аутентификация: `Authorization: Bearer <JWT>`.
Формат ошибки: `{ "code": "...", "message": "...", "traceId": "..." }`.

### Аутентификация

| Метод и маршрут | Назначение | Права |
|---|---|---|
| `POST /api/auth/login` | вход, выдаёт JWT на 1 час | — |
| `GET /api/auth/me` | проверка токена, данные пользователя | авторизованный |

Тело `POST /api/auth/login`: `{ "login": "...", "password": "..." }`.
Ответ: `{ "token": "...", "user": { "id", "name", "login", "role" } }`.

### Ресурсы

| Метод и маршрут | Назначение | Права |
|---|---|---|
| `GET /api/resources?q=&location=` | каталог активных ресурсов с поиском и фильтром | — |
| `GET /api/resources/:id` | карточка ресурса | — |
| `GET /api/resources/:id/availability?date=YYYY-MM-DD` | занятые интервалы выбранной даты (без ФИО и целей) | — |
| `POST /api/admin/resources` | создание ресурса | admin |
| `PATCH /api/admin/resources/:id` | изменение и отключение ресурса | admin |

### Бронирования

| Метод и маршрут | Назначение | Права |
|---|---|---|
| `POST /api/bookings` | создание записи для текущего пользователя | авторизованный |
| `GET /api/bookings/my` | собственные записи | авторизованный |
| `GET /api/bookings/:id` | просмотр доступной записи | владелец или admin |
| `POST /api/bookings/:id/cancel` | отмена с проверкой прав и времени | владелец или admin |
| `GET /api/admin/bookings` | все записи с фильтрами | admin |
| `GET /api/admin/audit` | просмотр аудита | admin |

`POST /api/bookings` требует заголовок `Idempotency-Key` (UUID от клиента).
Тело: `{ "resourceId", "startTime", "endTime", "purpose" }`.
Ответ 201: созданная бронь. Повтор с тем же ключом и телом — та же бронь (200).

### Служебные

| Метод и маршрут | Назначение |
|---|---|
| `GET /health/live` | процесс жив |
| `GET /health/ready` | готов обслуживать (проверяет БД; 503 без деталей) |

### Коды ошибок

| Код | Когда |
|---|---|
| 400 `VALIDATION` | неверные поля (шаг, диапазон, длина цели и т.п.) |
| 401 `NO_TOKEN` / `BAD_TOKEN` | нет токена / токен истёк или подделан |
| 403 `FORBIDDEN` | нет административной роли |
| 404 `NOT_FOUND` | ресурса нет или чужая запись недоступна |
| 409 `TIME_CONFLICT` | «Ресурс уже занят в выбранное время» |
| 409 `IDEMPOTENCY_MISMATCH` | тот же ключ, другие данные |
| 500 `INTERNAL` | непредвиденная ошибка (без внутренних деталей) |

## Защита от конкуренции

Проверка «свободно → вставить» без блокировки недостаточна: два параллельных запроса
могут одновременно увидеть свободный интервал и оба вставить запись.

**Применённый механизм:** транзакция с блокировкой строки ресурса.

Все пути создания бронирования (`POST /api/bookings`) и изменения ресурса
(`PATCH /api/admin/resources/:id`) соблюдают единый порядок блокировок:

```sql
BEGIN;
SELECT id, is_active FROM resources WHERE id = $1 FOR UPDATE;  -- блокируем строку
-- проверка is_active
-- проверка пересечения с Active-бронированиями
INSERT INTO bookings ...;
INSERT INTO idempotency_keys ...;
INSERT INTO audit_events ...;
COMMIT;
```

- `FOR UPDATE` сериализует конкурирующие создания для одного ресурса.
- Работает при нескольких экземплярах приложения (блокировка в БД, не в памяти).
- Конкурентное отключение ресурса использует ту же строку в том же порядке.
- Ожидаемый конфликт превращается в `409 TIME_CONFLICT`; после отказа
  частично сохранённых данных не остаётся (ROLLBACK).

См. `server/src/services/booking.js` (создание) и `server/src/routes/admin.js` (отключение).

## Защита от дублей (идемпотентность)

Клиент перед первой отправкой создаёт случайный UUID и отправляет его
в заголовке `Idempotency-Key`. При повторе того же действия — тот же ключ и те же данные.

- Сервер связывает ключ с пользователем, нормализованными данными (sha256) и результатом создания.
- Повтор с тем же содержимым возвращает исходную бронь без новой вставки.
- Тот же ключ с другими данными — `409 IDEMPOTENCY_MISMATCH`.
- Создание брони и сохранение ключа — одна транзакция; уникальность ключа обеспечивает БД (`UNIQUE(user_id, key)`).
- Одновременные повторы одного ключа: нарушение уникальности перехватывается и возвращает исходный результат, а не 500.

## Технические журналы и аудит

- **Технические журналы** (`pino`) — диагностика ошибок и отказов доступа.
  В каждом ответе об ошибке есть `traceId`; по нему находится событие в логах.
- **Аудит** (таблица `audit_events`) — история создания и отмены броней,
  изменения и отключения ресурсов: время, исполнитель, действие, объект, результат, `traceId`.
- Не журналируются: пароль, JWT, заголовок `Authorization`, секреты подключения.
- Доступ к аудиту через интерфейс — только администратор.

## CI/CD

GitHub Actions (`.github/workflows/ci.yml`):

1. checkout
2. установка Node 24
3. `npm ci` в `server/`
4. `npm run lint`
5. проверка миграций (`node-pg-migrate up --dry-run`)
6. `npm pack --dry-run` — артефакт
7. публикация (при успехе)

Секреты хранятся в **Settings → Secrets and variables → Actions**.
В репозитории есть только `.env.example` с именами переменных и безопасными плейсхолдерами.

При ошибке сборки публикация блокируется — конвейер красный, артефакт не выпускается.

## Запуск проекта

### Требования

- Node.js ≥ 20 (проверено на 24)
- npm
- Docker Desktop
- Git

### 1. Клонирование

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd bron-bez-konfliktov
```

### 2. Переменные окружения

Скопируйте образцы и заполните локальными значениями:

```bash
cp server/.env.example server/.env
```

В `server/.env` укажите:

```
DATABASE_URL=postgres://bron:bron_pass@localhost:5432/bron
JWT_SECRET=<любая_длинная_строка>
PORT=3000
```

### 3. Запуск PostgreSQL и pgAdmin

```bash
docker compose up -d
docker compose ps
```

Ожидается два контейнера `Up`: `bron_db` и `bron_pgadmin`.

pgAdmin: http://localhost:5050
Логин/пароль pgAdmin — в `docker-compose.yml` (`PGADMIN_DEFAULT_*`).
Подключение к БД из pgAdmin: Host = `db`, Port = `5432`, DB = `bron`,
User = `bron`, Password = `bron_pass`.

### 4. Установка зависимостей

```bash
cd server
npm ci
```

### 5. Миграции и учебные данные

```bash
npm run migrate up
```

Создаются таблицы и учебные данные:
- пользователи: `user1`, `user2`, `admin`;
- 5 переговорных комнат;
- 2 демонстрационные брони (Active и Cancelled).

### 6. Запуск приложения

```bash
npm run dev
```

Адрес приложения: **http://localhost:3000**
Проверка готовности: http://localhost:3000/health/ready

### 7. Демонстрационные учётные записи

| Логин | Пароль | Роль |
|---|---|---|
| `user1` | `Passw0rd!` | user |
| `user2` | `Passw0rd!` | user |
| `admin` | `Passw0rd!` | admin |

Пароли демонстрационные, реальные данные не используются.

### 8. Остановка

```bash
# остановить приложение: Ctrl+C в терминале сервера
docker compose down          # остановить контейнеры, данные сохраняются в volume
docker compose down -v       # остановить и удалить данные БД (осторожно)
```

### Порт 5432 занят?

Если на компьютере уже есть PostgreSQL, поменяйте в `docker-compose.yml`
проброс порта на `"5433:5432"` и в `server/.env` укажите `:5433` в `DATABASE_URL`.

## Резервное копирование и восстановление

Подробная инструкция — `docs/backup.md`. Кратко:

1. Создать контрольную будущую бронь, записать её id.
2. Сделать копию:
   ```bash
   docker exec bron_db pg_dump -U bron -d bron -Fc -f /tmp/bron.dump
   docker cp bron_db:/tmp/bron.dump ./bron.dump
   ```
3. Восстановить в отдельную тестовую БД:
   ```bash
   docker exec bron_db createdb -U bron bron_restore
   docker cp ./bron.dump bron_db:/tmp/bron.dump
   docker exec bron_db pg_restore -U bron -d bron_restore /tmp/bron.dump
   ```
4. Подключить тестовый экземпляр сервиса к `bron_restore`.
5. Проверить: вход, ресурсы, контрольная бронь, ограничения (пересечение, длина цели).
6. Зафиксировать команды, версии, результат и место безопасного хранения копии.
   Секреты в инструкцию не включать.

Рабочую БД для демонстрации не удалять.

## Диагностика

- **Где логи:** вывод процесса `npm run dev` / `npm start` (в проде — stdout контейнера).
- **Как найти ошибку по traceId:** взять `traceId` из ответа об ошибке,
  найти в логах запись с этим `traceId`.
- **Проверить БД:** `docker exec -it bron_db psql -U bron -d bron -c "\dt"`.
- **Проверить готовность:** `curl http://localhost:3000/health/ready` (200 — готов, 503 — БД недоступна).
- **Проверить живость процесса:** `curl http://localhost:3000/health/live`.

## Ограничения объёма

Реализованы две роли (user, admin). Не реализуются: оплата, сложный графический
календарь, повторяющиеся бронирования, уведомления, несколько часовых поясов.
Время существующей записи не редактируется: пользователь отменяет её и создаёт новую.
Все данные учебные, реальные персональные данные и секреты не используются.
